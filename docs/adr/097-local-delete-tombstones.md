# 097 local-delete-tombstones
epic: none · pr: none

## Decisions
- @delete @session @tombstone — Deleting a planner from the personal header branches on whether a login is live, not on the row. With a live session the row is deleted on the server as before, a 404 still counting as done. With no live session the header writes a `tombstone:{id}` row to IndexedDB carrying the `syncVersion` the local copy had, removes the planner row, and sends nothing. IndexedDB outlives cookies and nothing purges local planners when the login lapses, so a browser routinely holds synced planners while the app is a guest; every Delete in that state produced a 401 the client rendered as a generic error with the dialog left open, measured at roughly seven guest 401s for every successful delete. REJECTED: gating Delete on `isAuthenticated` — for a synced row it deletes only the local copy, the server row survives, and the next pull resurrects it with no explanation. REJECTED: a typed 401 with a "sign in to delete" toast — it turns a one-click action into a detour and adds nothing for the offline case a member hits.
- @delete @tombstone @neverSynced — A never-synced row is not special-cased: as a guest it is tombstoned like any other row, and its sweep answers 404 and clears. Local metadata cannot identify a never-synced row: the schema requires a positive `syncVersion` defaulting to the same value the server assigns on first create, and ADR 096 retired `savedAt`. REJECTED: skipping the server for a row whose `syncVersion` equals the initial value — that reads a row synced once as never synced, deletes only its local copy, and the next pull resurrects it.
- @sync @tombstone @sweep — The sync pass reads tombstones before partitioning and orders the sweep before the pull. A tombstone whose server row still carries the tombstoned `syncVersion` is swept with a DELETE and its server row is excluded from the pull; one whose server row advanced is dropped and the row pulled, so an edit made on another device beats a stale deletion; one whose server row is absent or already tombstoned is dropped. REJECTED: comparing the tombstone's `deletedAt` with the row's `lastModifiedAt` — device clocks are not comparable, and `syncVersion` is the server-assigned monotonic ordering the partition already uses. REJECTED: last-writer-wins — one integer comparison is the whole cost of not destroying another device's edit.
- @sync @tombstone @ownership — A sweep answered 204, 404, or 403 clears the tombstone; any other failure keeps it for the next pass. Local metadata carries no account and the server already enforces ownership on DELETE, so a 403 is read as "not this account's row" without the client ever storing an owner. REJECTED: recording the account in the tombstone — the guest that writes it does not know the account, and `userId` was removed from local metadata deliberately.
- @delete @tombstone @unauthorized — A 401 answered to the member path is the same case one click later: the delete mutation reports `unauthorized` as an outcome rather than a failure, and the header tombstones and cleans up exactly as for a guest. The client raises a typed `UnauthorizedError` for 401 so the outcome is decidable without matching a message. REJECTED: leaving 401 as a bare error and toasting it — a login lapsing between page load and click is the one window the login branch cannot see, and it produced the same generic toast this record exists to remove.
- @storage @tombstone — A tombstone is a row in the existing object store under its own key prefix, validated by its own schema on read. List readers filter by the planner prefix and never see it, and no database version bump is needed. REJECTED: a `deletedAt` flag on the planner row — every list reader would have to filter it.

## Takeaway
- takeaway: when the client cannot prove what the server holds, record the intent and let the server's answer settle it; a local-first write path needs a local-first delete path, and "absence" on either side is never evidence.
