# 074 planner-storage-key-v2
epic: none · pr: none

## Decisions
- @storage @keys @indexeddb — IndexedDB planner keys collapse from `planner:md:{deviceId}:{plannerId}` to `planner:{plannerId}`, migrated by copy, verify and delete inside the single `versionchange` transaction of `onupgradeneeded` at database version 2, with `deviceId` staying inside the stored value where sync attribution reads it. The device segment partitions a store that is already scoped to one browser profile, so it buys no isolation, and a regenerated `deviceId` orphans every row written under the old one; category and type are recoverable from the value, so they are decoration in the key as well. REJECTED: a dual-read legacy-key path kept open for a deprecation window — an IndexedDB migration runs on the next open, so the database version is the marker and there is no interval of user behaviour for a window to cover. REJECTED: reusing `metadata.schemaVersion` as the marker — that field versions the per-planner content schema, and one field tracking two independent axes cannot say which of them moved. REJECTED: migrating outside `onupgradeneeded` — the `versionchange` transaction is the only one permitted to touch schema and the only one that blocks concurrent readers, which is precisely the atomicity a copy-verify-delete over every row needs.
- @storage @errors — `storage.getItem` returns `Result<string | null, StorageReadError>`, so absence is `ok(null)` and an IO failure is `err`, and a failed open no longer caches its own rejected promise. A read that swallows its error into null is what mints a fresh `deviceId` on a transient failure, which is the generator of the orphaned rows the key change is cleaning up; the two are one defect seen from either end.
- @storage @keys @collision — Rows carrying the same planner id from different orphaned device scopes collide under the new key and are resolved newest `lastModifiedAt` wins. Every key build and parse site flips in the same change, which requires the hand-rolled builder in the router to be gone first — the title read behind it moves into the planner slice — and the open path gains `blocked` and `versionchange` handlers, since a schema bump now has a tab that can be holding the database open.

## Takeaway
- takeaway: a key segment that names the writer looks like isolation and is actually a join condition, so the day the writer's identity is regenerated, every row it wrote becomes unreachable data that no query is wrong enough to find.
