# 072 observer-effect-outbox
epic: none · pr: none · supersedes: 048 @effects @observers · supersedes: 055 @comment @notification @stats

## Decisions
- @effects @observers @outbox — Every observer effect commits one `domain_events` row inside the transaction of its cause, and nothing else; an asynchronous dispatcher picks the row up in its own transaction — row-locked, idempotent, skip-if-dispatched — derives notification rows through `INSERT IGNORE` on a dedup key, and publishes SSE; a ShedLock'd scheduled relay re-dispatches rows whose `dispatched_at` is still null past a grace window; SSE stays a best-effort hint with client refetch as the delivery floor. An after-commit listener that itself writes rows under `REQUIRES_NEW` loses the push and the row together when the process dies in the commit-to-listener window, and on the recommended path a latch that is never reset makes that loss permanent; an `AFTER_COMMIT` listener runs on the request thread, so fan-out with no bound on its size is paid by the response; and per-path coupling policy drifts in practice, one path having inverted its own written record inside a day. This applies uniformly, so comment and reply notifications move onto the same path. REJECTED: notification rows written inline in the caller's transaction, chosen per path by fan-out size — the selection criterion is itself the drift vector, and an unbounded fan-out inside the caller's transaction extends a write transaction by the size of the audience. REJECTED: `REQUIRES_NEW` writes from after-commit listeners — the crash window above, with no durable record to retry from. REJECTED: leaving the two paths that already lose events as they are — the recoverability invariant stated by `048 @effects @observers` is violated by both, and an invariant that survives its own counterexamples is not one.
- @effects @observers @latency — Notification visibility is bounded below by the dispatcher and above by the relay interval, and the worst case is the relay interval. The dispatcher is what makes derivation guaranteed rather than prompt, and any tighter bound would have to come back through the caller's thread.
- @effects @outbox @pushes — Effect arms enqueue their SSE pushes and the dispatcher fires them from an after-commit synchronization, strictly after `dispatched_at` and the notification rows are durable; each push is individually isolated so one failure drops neither its siblings nor the committed dispatch. A push inside the dispatch transaction is observable before, and without, the commit: a dispatch that pushes and then rolls back leaves the recipient holding a notification no refetch will confirm, and the relay's re-run pushes it again — a phantom heals never, a lost push heals on the client's next refetch of the committed row. REJECTED: pushing from inside the arm — the shape that pays Redis I/O and retry backoff while holding the event row lock, with the phantom window as its failure mode.
- @effects @outbox @poison — Dispatch attempts are counted in a `REQUIRES_NEW` transaction so a failing arm still persists its increment; the relay scan excludes rows at the attempt cap, and the alarm fires from the failure path when the count has reached the cap — not from the increment, which would page for an attempt that then succeeds. Capped rows stay in the table, re-read and discarded by the scan at a cost proportional to the poison count, with retention a manual operations action. An uncapped queue ordered by age and bounded by batch size lets a fixed set of deterministically failing rows permanently occlude every younger event — fleet-wide effect stoppage with only repeated exception noise as signal. REJECTED: counting attempts in the dispatch transaction — the rollback that defines a failed attempt erases the evidence that it happened.
- @effects @outbox @routing — The relay's pending-row scan runs in a read-write transaction so it reads the primary; the per-row dispatches keep their own transactions. An untransacted scan inherits the repository default of `readOnly = true`, which the routing datasource maps to the replica — handing the recovery component, whose one job is to see what the primary-side path failed to do, a replication-lagged view of `dispatched_at`. REJECTED: one transaction around the whole relay batch — it would serialize every dispatch into a single commit and hold the scan's view for the duration.
- @effects @outbox @eligibility — An ids-only payload obliges the arm to re-read state at dispatch, and the re-read must carry the raise site's predicate: the publish and recommend arms skip a planner no longer published, the comment arms skip a soft-deleted comment. Re-reading by bare id defeats the stale-payload invariant it implements — the row returns, but the state it announces (a withdrawn publication, a deleted comment's placeholder text) is the stale value the design promises cannot be announced.
- @effects @archunit — Enforcement narrows to two statements: notification rows are written only by the dispatcher, and after-commit listeners reach only the dispatcher. The rules the previous placement needed described which effects may write where, which is exactly the per-path judgment that drifted.
- @effects @tests — `EffectPlacementIT` asserts the chain rather than the listener: rollback yields no event row and therefore nothing ever derived, commit yields an event row and relay-guaranteed derivation, and a process death between commit and dispatch still ends in derivation.
- @effects @outbox @replay — `domain_events.id` is a server-side sequence, usable as a replay cursor by a consumer that keeps a position, and deliberately unused now. A cursor retrofitted onto rows already written is a cursor over a gap; the sequence costs nothing to have from the first row.

## Takeaway
- takeaway: an effect that must survive a crash has to be *written* by the transaction that causes it, not *triggered* by it — a listener that fires after commit and then writes its own row has two failure points where the design claims one, and the durable record it would retry from is the row it never got to write.
