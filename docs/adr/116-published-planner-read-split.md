# 116 published-planner-read-split
epic: none · pr: none

## Decisions
- @read-split @cache — A published planner is read through four endpoints: `GET /api/planner/md/published/{id}` returns the content every viewer sees alike, `GET .../{id}/stats` the counts, `GET .../{id}/flags` the caller's own flags, and `POST .../{id}/viewcount` records a view. A response that varies by viewer or carries a side effect cannot be served from a shared cache, and the single detail read did both: it carried five per-viewer flags and recorded a view on every fetch.
  REJECTED: one endpoint that stays uncached, with the planner assembled from Redis — origin time for the detail read is 11–21 ms against a client-to-edge leg of roughly 300 ms from Korea, so a server-side cache removes time no reader feels; as a read path during a database outage it covers only the planner body while authentication, comments and the list still fail, and it adds a second copy that every eviction event must reach.
  REJECTED: one endpoint varying on the auth cookie — the edge cache key ignores cookies, and the view side effect would still require every read to reach the origin.
- @content @cookies — The content read is fetched with credentials omitted and answered without `Set-Cookie`; neither the device-id nor the CSRF cookie is minted on it. An origin `Set-Cookie` makes Cloudflare bypass the cache, measured through the real edge, and a request that carries no cookies cannot be personalized by accident.
- @content @ttl — Content is served with `Cache-Control: public, max-age=60, s-maxage=604800`, a Cache Rule makes the path eligible, and the cache key ignores the query string. JSON is never eligible without a rule; the short browser lifetime exists because a purge reaches only the edge, and an ignored query string keeps cache-busting parameters from multiplying origin misses.
- @content @purge — Correctness comes from purge, not from the lifetime: an outbox effect purges the content URL by URL on edit, unpublish, moderation removal, delete, author rename (every planner of that author), account deactivation and hard delete. Timing constants never carry correctness (ADR 008), and a takedown that waits for a TTL keeps serving what was taken down; the outbox retries a failed purge instead of losing it. The purge is issued once, after the Seoul replica has applied the write's GTID (`WAIT_FOR_EXECUTED_GTID_SET`); while it lags the effect retries, so the origin can no longer serve the old body by the time the edge is told to drop it.
  REJECTED: purging immediately on commit — a reader reaching the lagging Seoul origin re-caches the old body for the full lifetime.
  REJECTED: purging twice, immediately and again after the replica catches up — the first purge only lets the edge re-cache the same stale body from Seoul, doubling calls for no reader-visible gain.
  REJECTED: relying on the seven-day lifetime — a takedown would stay public for up to a week.
  REJECTED: versioned content URLs — they spare the purge on edit, but a takedown still leaves the old URL cached, so the purge path is needed regardless and the version adds a second key to keep coherent.
- @content @404 — A missing or withdrawn planner's 404 is not cached. A republish must be visible at once, and repeated misses on unknown ids are already bounded by the per-IP public-read limit and the replica-miss bulkhead.
  REJECTED: a short negative cache — absorbs repeated misses at the price of a republish staying invisible for the window, at a traffic level that has no miss problem.
- @viewcount — A view is recorded only by `POST .../viewcount`, sent by the mounted page, never by a GET or a route loader. Loaders run on prefetch and a GET is fetched by caches and preloads, so either would count views that are not visits. Recording is best-effort through the Redis view counter (ADR 131).
- @stats — The counts are never cached, at the edge or in the browser. They change on every view, vote and comment, and ADR 010 permits counts to be inexact but not stale by a fixed window, so a lifetime would be a timing constant with no event to purge it.
  REJECTED: a lifetime of a few seconds — absorbs repeated reads of one planner, at a traffic level where the stats read costs one replica query.
- @ratelimit — Each split read has its own per-client bucket: the content read keeps the public-read bucket, stats and flags share a planner-stats bucket, and the view recorder has its own smaller bucket. One page visit calls all four endpoints, so a shared bucket would quarter the visits a client can make, and an endpoint with no bucket of its own is an unmetered path for load against the database and Redis.
  REJECTED: one shared public-read bucket raised fourfold — every endpoint could then be driven at the combined rate, and a throttled view would share a budget with reading.
  REJECTED: leaving stats, flags or viewcount unmetered — they reach the replica and the auth Redis on every call.
- @flags — Flags are per viewer and never shared-cached, and the page does not request them for an anonymous viewer, whose flags are all false.
- @flags @fields — The flags are `hasUpvoted`, `isSubscribed` and `ownerNotificationsEnabled`; the detail read's `isBookmarked` and `hasReported` are not carried over. No page reads either, and no client bookmarks or reports a planner, while a field added to a new endpoint later breaks no client and one removed later does.
  REJECTED: carrying all five — freezes two fields with no reader into a public contract.
- @rollout — The content path keeps its URL and changes its shape, and the frontend and backend deploy separately, so the split lands in order: the backend adds `stats`, `flags` and `viewcount` beside the unchanged detail read; the frontend moves to the four endpoints; the backend then strips flags and view recording from the detail read and sets its cache headers; the Cache Rule is enabled last. The detail read keeps its old shape until the frontend release reading the four endpoints is live in production.

## Takeaway
- takeaway: a shared cache can only hold what is the same for everyone and harmless to fetch twice; splitting the read along those two lines is what makes it cacheable, and the cache itself is the smaller part of the work.
