# 044 react-lint-plugin-hosting
epic: none · pr: none

## Decisions
- @lint @react — The React rules oxlint has no native implementation of are loaded as an oxlint JS plugin, which oxlint runs in-process, rather than by reintroducing eslint as a second runner. One command still lints the tree, and the rules that only exist as an eslint plugin become reachable without a second parse of every file. REJECTED: an `eslint` pass alongside `oxlint` — doubles the parse cost and splits enforcement across two configs whose overlapping rule sets drift silently. REJECTED: waiting for oxlint to port the compiler rules natively — the rules that matter here are the compiler's own diagnostics, which track the compiler's release cadence rather than the linter's.
- @lint @react — The JS plugin is registered under the alias `reacthooks`, because `react` and `react-hooks` are reserved for oxlint's native Rust implementations and a JS plugin may not claim either. The consequence accepted is that an `eslint-disable-next-line react-hooks/<rule>` comment does not suppress the aliased plugin's same-named rule: the two namespaces are unrelated to the suppression machinery. REJECTED: dropping oxlint's native react plugin so the JS plugin could take the real name — trades a fast Rust implementation of the whole correctness category for a slower JS one, to buy back a suppression syntax that should be rare.
- @lint @react — `exhaustive-deps` and `rules-of-hooks` stay on oxlint's native pair and are deliberately *not* enabled from the aliased plugin, so exactly one implementation of each reports and the familiar suppression comment keeps working against it. The aliased plugin contributes only rules with no native counterpart. REJECTED: enabling both implementations — every genuine violation reports twice, and only one of the two answers to a suppression comment, so silencing a finding leaves half of it on screen.
- @lint @react — `react-perf` is rejected outright rather than enabled at warning level. Its rules forbid inline object, array, and function props, which is precisely the manual memoization this codebase removed when the React Compiler took over that work; enabling it produces over a thousand findings that all instruct the reader to undo a deliberate direction. REJECTED: enabling it with the object/array rules disabled — what remains is the function-prop rule, which carries the same instruction and the bulk of the findings.
- @lint @react (taste) — Rules that report real findings the project has not yet chosen to fix are carried at warning severity in the same config, and the lint command no longer promotes warnings to failures; severity in the config is what decides whether a rule blocks. The alternative keeps a rule honest only by leaving it unenforced in a second file nobody runs. REJECTED: a separate advisory config and a second command — it was already structured that way, and the advisory rules went unread because nothing invoked them.
- @lint @compiler — React Compiler bailouts are gated by a checked-in allowlist that fails the build on any file not already named, rather than left as invisible per-file deoptimization. A file silently dropping out of compilation is indistinguishable from one that never compiled, so without the gate the set only grows. The compiler is incompatible with Babel 8, and the check resolves Babel through the bundler's own nested Babel 7 for that reason: under the hoisted Babel 8 the same tree reports 89 bailouts instead of 9. REJECTED: a bare count threshold instead of a file list — a threshold lets a newly broken file hide behind a newly fixed one.
- @lint @compiler — The compiler's `rule-suppression` rule is enforced, because a suppression comment for a React lint rule makes the compiler skip the whole component, turning a narrow lint waiver into a silent opt-out from compilation. That coupling is invisible at the suppression site and was already costing one hook its compilation. REJECTED: relying on the bailout allowlist alone to catch it — the allowlist names the file but not the cause, so the fix looks like restructuring code that is in fact fine.

## Takeaway
- takeaway: a lint waiver that a compiler also reads is not a lint waiver, so any suppression syntax shared with a build tool needs a rule watching the suppressions themselves.
