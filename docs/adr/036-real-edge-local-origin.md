# 036 real-edge-local-origin
epic: none · pr: none · supersedes: 035 @staging @environment

## Decisions
- @staging @environment — End-to-end tests reach the application through production's own Cloudflare edge — real tunnels, hostnames, TLS and WAF — while the origin behind that edge is the local compose stack, so no AWS staging environment exists. A full copy was built, run, and torn down: of the defects it surfaced, exactly one could not have been found locally, and it was the WAF answering the JDK's default user agent with an HTML 403 on the backend's outbound token exchange, which would have shipped a broken login. Everything else it caught reproduced on containers once the containers were configured honestly. The property worth paying for is that the client traverses the real path; the property being paid for was that the origin mirrors production. REJECTED: the 1:1 copy in its own account — a Multi-AZ database, a cross-region replica and two fleets per run, ninety minutes to stand up, and a long tail of environment-only failures that bought origin fidelity no defect required. REJECTED: local containers only — cheapest, and it covers more than assumed, since deterministic replication delay exercises the read gate better than a fast real replica does, but it cannot see the edge at all and the one defect that would have reached users lived precisely there. REJECTED: production smoke tests instead of a pre-merge gate — catches edge defects only after the release is live, which is no help for a migration whose rollback is a snapshot restore.
- @staging @geo — Geo steering by genuine client geography is untestable, because the edge derives a client's region from the connection and two tunnels terminating on one host are two paths to one place. Pool failover stays testable by disabling a pool; "a client in this region is served by that region" does not.
- @staging @replication — Cross-region replication is exercised by the local two-region rig rather than by real distance, so latency-shaped failures stay invisible.
- @staging @coverage — Identity policy, cross-account image distribution and secret delivery lose their end-to-end coverage; they are exercised only by the production deploy itself.
- @staging @blast-radius — The edge is shared with production, separated by hostname prefix, so a mistake in that stack can affect production DNS — which the isolated design made impossible.

## Takeaway
- takeaway: fidelity is not one axis. Split the defects by where they live, pay full price only for the path they live on, and the copy of everything else turns out to be the expensive half that catches nothing.
