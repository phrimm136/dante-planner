# 037 verification-lanes-and-continuous-deployment
epic: none · pr: none

## Decisions
- @testing @lanes — An e2e spec's lane is the set of changes that can break it: application suites, contract suites, and infrastructure suites are distinct Playwright projects selected by filename suffix, with `.infra.spec.ts` joining the existing `.contract.spec.ts` convention. The suffix makes the classification travel with the file and keeps the partition greppable. REJECTED: directory-per-lane — loses the flat listing and makes every reclassification a move that churns imports. REJECTED: in-file tag annotations — invisible in a directory listing, and the runner's project selection would depend on parsing test bodies.
- @ci @gates — Verification attaches to events, not refs. The pull-request event runs change-filtered blocking lanes; the trunk push event runs every lane unconditionally; the deploy pipeline consumes only the trunk run's verdict. Change detection is a first job emitting per-area outputs consumed by job-level conditions, because branch protection counts a skipped job as satisfied while a workflow that never triggered reports nothing and wedges the merge. REJECTED: workflow-level path filters with required checks — structurally incompatible, the wedge is permanent. REJECTED: a merge queue — closes the stale-base race at per-merge latency and puts a third party in the merge path; the unconditional trunk run catches the same race minutes later at zero merge cost, and a paged revert is acceptable for a single-maintainer trunk.
- @ci @security — Lanes holding no credentials run for fork pull requests under the platform sandbox; lanes that assume cloud roles run only for same-repository pull requests and under the deploy environment, whose role trust is conditioned on the repository identity a fork cannot forge. The `pull_request_target` event is never combined with a checkout of the head. REJECTED: secrets-bearing lanes gated by contributor approval alone — approval guards the first run, not the pattern.
- @deploy @cd — Deployment is continuous: the trunk run's success triggers the deploy workflow, which checks out the exact commit that run verified, and the resulting manifest-bump commit carries a CI-skip marker so the chain cannot trigger itself. The deploy concurrency group keeps one running and one pending run, so rapid merges coalesce and only the newest pending commit deploys. REJECTED: human-dispatched deploys — the manual bump was the only non-automated link in an otherwise reconciled path, and it made release cadence a memory task. REJECTED: deploying the trunk head instead of the verified commit — a merge landing mid-pipeline would ship under the previous merge's verdict.
- @deploy @edge — The edge tier (production's real Cloudflare edge fronting the local compose origin) runs inside the deploy pipeline, after the image build and before the node surge and manifest bump, against a standing staging edge stack whose tunnel tokens and endpoints it reads from the secrets store. It gates releases, not merges: a red edge run halts deployment while trunk keeps moving. REJECTED: the edge tier as a merge gate — puts third-party availability and a quarter-hour in the path of every merge, which erodes the merge-daily habit trunk-based development depends on. REJECTED: applying and destroying the edge stack per run — the stack is configuration on the zone production shares, and churning its DNS, tunnels, and access policies once per merge multiplies the one mistake class the shared-zone consequence already admits.
- @ops @rehearsal — The full-copy staging environment becomes a dispatch-only rehearsal capability, invoked before changes only it covers: stop-the-world migrations, cluster and secrets-machinery upgrades, trust-topology changes. Its previous trigger fired on promotion from a branch this record retires, so as a gate it would be unreachable code holding a live cloud role. REJECTED: deleting the workflow — the rehearsal capability is the cheap form of the environment, and rebuilding it from nothing was measured in sessions. REJECTED: keeping it as a standing gate — its defect yield never justified its cost, which is the finding that reshaped the whole environment strategy.
- @testing @regions — Region-specific behavior is asserted through per-region DNS pins, a hostname per region pointed at that region's tunnel, and geo steering by genuine client geography stays untested, extending the consequence 036 accepted. The pins bypass steering, so they prove the properties that matter from any vantage point: cross-region cookie carriage, per-region degradation scope, and pool failover observed by disabling a pool. REJECTED: ephemeral in-region probe runners — honest geography and latency, but a per-run instance lifecycle (launch, credential feed, teardown) standing behind a single assertion class. REJECTED: proxied egress from the CI runner — honest classification with fictional latency, and it still needs an in-region machine, so it inherits the probe cost without the probe fidelity.
- @git @trunk — The default branch is the only long-lived ref; the two former environment branches retire behind archive tags once provably merged. Merges land by rebase only, because the repository's per-commit message discipline is only worth its cost if those commits survive to trunk; branch protection requires a pull request and the blocking lanes, and head branches auto-delete at merge. REJECTED: squash merges — flatten a crafted commit series into one message written in a merge dialog, silently erasing the discipline. REJECTED: merge commits — preserve the commits but braid the history that every downstream tool now assumes is linear.

## Takeaway
- takeaway: gates attach to events, and branches are justified only by a gate no other ref can host — so cheapening a gate dissolves the branch that buffered for it, and the cost of each verification tier should be proportional to the rarity of the event that triggers it.
