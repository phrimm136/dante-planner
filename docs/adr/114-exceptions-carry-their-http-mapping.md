# 114 exceptions-carry-their-http-mapping
epic: none · pr: none

## Decisions
- @errors @conventions — An exception the application owns carries its own HTTP mapping: `DomainException` extends `ErrorResponseException`, derives its status from `ErrorKind`, and puts its code on the RFC 9457 body as a `code` property. One rendering advice extends `ResponseEntityExceptionHandler`; an explicit `@ExceptionHandler` exists only to translate an exception the application does not own (driver, Redis, Tomcat) or to perform a response mutation an exception cannot carry (the cookie clear on a revoked session). Feature packages keep throwing with a kind and never name a status; the kind-to-status table lives on the base class in `shared.exception`, the package that already holds the advice.
  REJECTED: one handler per business error (30 handlers, 25 of them returning a body the exception could have carried) — every new error is an edit to the advice, the advice imports every feature's exceptions, and the Sentry and log side effects drift across copies.
  REJECTED: keeping `ErrorKind` transport-neutral by mapping to a status inside the advice — `ErrorResponseException` needs the status at construction, and the boundary that matters, features not knowing HTTP, is preserved by the kind; the base class knowing HTTP is what Spring's own `ErrorResponseException` already is.
- @errors @body — The body is RFC 9457 problem JSON with `detail` as the operator-facing text and `code` as the client-facing identity; the frontend maps codes to its own i18n keys, so `detail` is not localized and `MessageSource` resolution is left alone. The `{code, message}` record and its `application/json` content type are removed. For the deploy window every body also carries `message` as a mirror of `detail`, set in the one filler that builds bodies, so the frontend reads `detail` alone and declares neither `message` nor `status` (the RFC calls `status` advisory; the HTTP status line is authoritative and is what the client dispatches on). The mirror is one constant and one line, removed by a backend commit once the frontend release reading `detail` is live in both regions.
  REJECTED: a `type` URI as the error identity, the RFC-idiomatic form — the frontend contract already keys on `code`, and a second identity buys nothing a reader would use.
  REJECTED: a deprecated `message` fallback on the frontend — the frontend and the backend deploy from different systems, so the window exists whichever goes first, and tolerance on the side that needs a client release to remove it outlives its window; a body that fails a required field also rejects the whole document, which silently disabled the fallback it was meant to be.
- @errors @operator — An owned exception's operator channel is the throwable itself: `getMessage()` is the complete operator text, computed by the subclass from its own fields where it differs from the client `detail`, and the stack trace rides with it. `DomainException` holds no fields; status comes from the one-argument `ErrorResponseException` constructor, code and detail live on the body, and `reportable()` is the one policy bit. Sentry capture and the warn line run once, in the advice's `handleExceptionInternal` override; owned errors log at warn without the trace, and only the catch-all and the I/O failure branch log at error with it, so an expected 404 costs one line and an alert-worthy failure carries its trace to Sentry. The OAuth failure therefore drops from error to warn, with capture unchanged.
  REJECTED: stored operator strings and per-subclass getters (`logDetail`, `originalCode`) — four channels that each preserved one deleted handler's text, needing `instanceof` branches in the seam, while Spring's composed `getMessage()` leaked into Sentry values.
  REJECTED: printing the stack trace on every owned error — the trace of an expected 404 always ends at the same `orElseThrow`, and the incident that motivated this record was fifty of them.
  REJECTED: `ErrorResponse.Interceptor` (6.2) as the seam — through `ResponseEntityExceptionHandler` the body reaches the entity processor wrapped in a plain `ResponseEntity`, so the interceptor is invoked with a null `ErrorResponse` and never sees the exception.
  REJECTED: keeping the captures in per-exception handlers — seven copies with small drift (some capture, some do not, one logs at error).
- @errors @boot — `spring.mvc.problemdetails.enabled` stays unset. It registers a bare `ProblemDetailsExceptionHandler` under `@ConditionalOnMissingBean(ResponseEntityExceptionHandler.class)`, so the subclass above is the bean it would otherwise create, and turning the switch on is a silent no-op.
- @errors @internal — `UsernameGenerationException`, an exhausted retry loop in a service, is not a business error and stays a plain `RuntimeException` rendered by the catch-all with Sentry capture; its dedicated code is dropped, and nothing in the frontend read it.
  REJECTED: making it a `DomainException` and wrapping the throw in a lambda to satisfy the guarantee-placement rule — the rule satisfied rather than obeyed.
- @errors @sse — The two async lifecycle exceptions (`AsyncRequestTimeoutException`, `AsyncRequestNotUsableException`) are swallowed at debug in a second advice ordered `HIGHEST_PRECEDENCE`. They reach the resolver after an `SseEmitter` has committed the response, so no status can be written; the emitter's own `onTimeout`, `onCompletion` and `onError` callbacks are the handling. The base rendering advice maps both types itself, so a second handler for either in the same class is a startup ambiguity error, and its own rendering would log a warn per stream timeout for a body it cannot send.
  REJECTED: overriding the base methods to return null — hands the exceptions to the default resolver on a committed response, whose behavior there was not verified, for no gain over a first-ordered advice.
- @errors @filters — Errors written before the dispatcher (authentication entry point, CSRF filter, auth degradation responder, the rate-limit interceptor's undeclared-policy branch) go through one `ProblemWriter` that takes a `ProblemDetail` and headers and serializes it as `application/problem+json`; the sites build the body with the same filler the advice uses, and the degradation codes, messages and `Retry-After` value come from one `DegradationErrorConstants` table read by both paths. A filter decides and writes, it does not throw, so the writer's input is the body, not an exception.
  REJECTED: a writer taking an `ErrorResponse` — constructing an exception in a filter only to serialize it.
  REJECTED: leaving the filter path as hand-written maps for a later unit — one site used `error` where the others used `code`, so a CSRF 403 had never matched a typed client error, and a client that declares `detail` cannot meet a producer that sends `message` alone.
- @errors @capacity — `SseCapacityExceededException` extends `ErrorResponseException` directly, not `DomainException`: it carries 429, `Retry-After` and its code the same way, but a full connection registry is a resource limit raised inside the SSE service, not a business rule, and the guarantee-placement rule confines `DomainException` construction in services to `orElseThrow` suppliers. The advice's warn line therefore keys on any `ErrorResponse`-implementing exception; Sentry keys on `DomainException.reportable()` alone.
  REJECTED: making it a `DomainException` behind a lambda — the rule satisfied rather than obeyed, as with the retry-loop exception above.

## Takeaway
- takeaway: the RFC 9457 model inverts the dependency: the exception knows its HTTP mapping and the advice knows nothing about business errors, so adding an error stops meaning adding a handler.
