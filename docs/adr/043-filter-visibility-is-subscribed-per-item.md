# 043 filter-visibility-is-subscribed-per-item
epic: none · pr: none

## Decisions
- @filter @render — A filtered list keeps its filter state in a store owned by `useSetFilters`, and each card subscribes to its own visibility through that store; the list container receives the store handle, never the selections, so a filter interaction re-renders only the toggled control and the items whose visibility actually changed, leaving sibling controls, the container and unchanged items at zero. Visibility as a derived prop is immune to memoization: the predicate returns a fresh `Set` per evaluation, so the `map` producing the card elements can never be cached, every element is new, and every card re-renders correctly because its `className` genuinely changed — on the identity browser that was 368 component executions and ~75 ms of render per toggle at 4× CPU throttle, for 184 cards. REJECTED: CSS-driven filtering, stamping `data-*` attributes at mount and driving visibility from generated selectors so zero cards re-render — it expresses the semantics fine, since hiding is a union of rules, AND-across-facets falls out of emitting one `display:none` rule per facet, ALL-within-a-facet emits one `:not([data-k*=" v "])` rule per selected value, and ANY-within-a-facet chains `:not()` in a single rule, but it moves the semantics out of `applyFacets` and the per-list facet descriptors into selector strings the per-list facet parity suites can no longer pin, the vitest DOM does not evaluate attribute-substring selectors from an injected stylesheet so list behaviour becomes untestable, and the empty state would need the whole predicate restated inside `:has()`. REJECTED: virtualization — measured slower than rendering once, and reverted.
- @filter @render — Any list whose `.map` callback reads shared filter state has already lost, whichever direction the state arrives from: the callback closes over a value that changes on every interaction, so the elements it builds are new every time and no memoization downstream can recover. The subscription has to terminate inside the item, not at the boundary that renders items.
- @filter @render — Every action a control receives keeps one identity for the control's lifetime, because granular subscription does nothing for a component that also takes a callback whose identity churns. The per-facet setters were rebuilt whenever any facet changed, so each control got a new `onSelectionChange` and re-rendered no matter how narrowly it read the state, which defeated the filter bar through a channel entirely separate from the list. REJECTED: narrowing each control's read further and leaving the setters alone — the callback prop alone is enough to invalidate the control, so the read has no bearing on the outcome.
- @filter @render @boundary — Per-item subscription is applied only where a filter flips few items, and the deck grids keep their container-derived list. The technique's price is one selector evaluation per subscribed item per store write, so on the deck grids 294 cards × 3 selectors run on every write while the benchmarked filter flipped ~170 of 184 cards: when a change flips nearly everything, redistributing the container's loop into the items pays the same total predicate work plus a subscription per item, and saves nothing. REJECTED: applying it uniformly for consistency — it was tried on the deck grids and cost more than it saved.
- @filter @render — The empty state is its own subscribed component rather than a visible-id set computed by the list container. REJECTED: leaving the container to compute that set — it costs one container render and a second full evaluation of the predicate per toggle, both of which the subscribed component removes, and it keeps the grid mounted so recovering from an empty result no longer remounts every card.
- @filter @state — `useSetFilters` owns `searchQuery` alongside the facet `Set`s and `resetAll` clears it, because the per-item predicate needs the query and the facets from one snapshot. The store is created per mount, so filter state still dies with the page. REJECTED: leaving the query in page-level state — each item would then read two independently updating sources per evaluation, and every page would compose its own reset.
- @filter @search — Search terms are precomputed per item as an array of lowercased strings, which is what makes each item evaluating its own predicate on every store change affordable: it is the same total work the container's loop did, redistributed. REJECTED: one concatenated haystack per item — a query could then match across the boundary between two unrelated terms.
- @render @memo — A dropdown option row is wrapped in `React.memo` and `SearchableMultiSelect` reads its selection through a ref so the toggle handler keeps one identity. The compiler cannot memoize elements built inside a `map`, so without the wrapper an option's own render is O(options) — revealing a batch re-rendered every already-revealed row, and toggling one option re-rendered all 343 — and a memoized row is worthless if its callback prop changes anyway. REJECTED: relying on the compiler alone here — the elements originate inside a `map`, which is exactly the position it cannot cache.

## Takeaway
- takeaway: moving work from a container into per-item subscriptions redistributes it rather than removing it, so the technique pays only where a change flips few items; measure the fan-out before adopting it, and treat a churning callback prop as enough to cancel the whole benefit.
