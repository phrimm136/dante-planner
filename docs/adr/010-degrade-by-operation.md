# 010 degrade-by-operation
epic: none · pr: none

## Decisions
- @degradation @availability (taste) — Degradation is scoped by operation, not by service: reads must survive write-path outages, and write outages surface as typed, user-explainable errors with client-side state preserved. REJECTED: whole-service health gating — it converts a write-path dependency failure into a total outage for readers who needed nothing from it.
- @health @readiness — Liveness and readiness report application health only; dependency failures raise alerts but never deroute traffic. REJECTED: dependency-aware readiness probes — a shared-fate outage would mark every pod in every region unready simultaneously, and routing away from a failure only helps when the failure is local.
- @auth @fail-open — Token blacklist checks read the region-local replica, accepting bounded staleness; when the store is entirely unavailable the check fails open and increments a dedicated counter that alerts. REJECTED: failing closed — it converts a cache outage into a total authentication outage, and the exposure is already bounded by the short access-token lifetime.
- @errors @typed — Degraded states are distinct wire codes for authentication and for writes, mapped in both the global exception handler and the authentication filter, because exceptions thrown inside a filter never reach `@RestControllerAdvice`. REJECTED: a single generic 503 — the client cannot choose between preserving a draft locally and prompting a re-login without knowing which subsystem failed.
- @timeouts @threads — Bounded cross-region connect and read timeouts are what make the typed degradation reachable. REJECTED: exception mapping alone — request and connection-pool threads exhaust against an unbounded socket timeout long before the typed exception is ever thrown, which takes reads down along with writes.
- @views @best-effort — View recording is best-effort: the loss of one flush window when a pod dies is accepted, and the client renders an optimistic increment. REJECTED: durable recording — it puts a synchronous write on a read-hot path, at full cross-region cost from the secondary region, to protect a counter whose exactness nothing depends on.
- @views @buffer @scheduling — Views accumulate in a per-pod in-memory buffer drained by a scheduled batched flush, deliberately not distributed-locked. REJECTED: an after-commit listener — it runs synchronously on the request thread, putting the cost back on the read it was meant to keep cheap. REJECTED: an executor — the codebase admits no application-managed thread pools.

## Takeaway
- takeaway: "is this operation available" and "is this service healthy" are different questions, and answering the first with the second is what turns a partial dependency failure into a full outage. Deciding per operation also forces the useful question of which data is allowed to be lost, which for a view counter is a cheaper answer than for anything else.
