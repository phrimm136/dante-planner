# 113 error-responses-ignore-endpoint-produces
epic: none · pr: none · supersedes: 064 @sse @capacity

## Decisions
- @errors @negotiation @sse — The rendering advice removes the request's producible-media-types attribute in the one method every rendered error passes through (`handleExceptionInternal`, which its explicit handlers also reach via a private `respond`), so no error response inherits the endpoint's `produces`. Spring stores the matched mapping's `produces` on the request and negotiates every `@ExceptionHandler` return value against it, and a body is written only where that set and the client's Accept intersect; on an event-stream endpoint the set is `text/event-stream` alone, so every entity-returning handler failed with `HttpMediaTypeNotAcceptableException` and the original exception escaped to Tomcat as a 500 (in production, a 404 for an unpublished planner on the comment stream, retried by the client for its full backoff budget because it never saw the 404). The client-side veto is defeated by Spring's own fallback for `ProblemDetail` bodies, which retries the intersection with `application/problem+json`; the endpoint-side veto has no framework fallback (the 6.2 and 7.x resolvers only ever set the attribute, never clear it, and spring-framework #35621 asking to preserve or reset it was declined), so the one custom piece is the clear.
  REJECTED: a `HandlerExceptionResolver` placed first in the chain that clears the attribute and resolves nothing — independent of handler discipline, but the house test pattern is `standaloneSetup` (`backend/src/test/CLAUDE.md` bans `@WebMvcTest` for context-cache cost), and a standalone builder replaces the resolver chain rather than extending it, so the resolver could only be proven by a full-context test; the advice-internal clear is exercised by one standalone test that throws every handler family on a `text/event-stream` endpoint.
  REJECTED: hand-writing the response in each affected handler (the shape the two 429 handlers had) — it fixes the instances someone noticed and leaves the class; three copies of hand-serialized JSON existed and the 404 path still had none.
  REJECTED: declaring `produces = application/problem+json` on the handlers, the 6.2 feature — handler selection filters by the client's Accept first, so a handler producing problem JSON is never chosen for `Accept: text/event-stream`.
  REJECTED: widening the frontend's Accept header alongside the clear — two sides of one contract changed for one client, and any plain client still receives a 500 for a 404; an error response must not depend on the Accept header.
  REJECTED: a converter that writes the error body as `text/event-stream` — labels JSON as an event stream on the wire, which the stream parser then tries to frame.

## Takeaway
- takeaway: content negotiation has two inputs with veto power, the client's Accept and the server's `produces`; a fix that neutralizes one and is tested against a client that happens to satisfy the other passes CI and fails in curl.
