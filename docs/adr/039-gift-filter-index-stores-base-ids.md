# 039 gift-filter-index-stores-base-ids
epic: none · pr: none

## Decisions
- @indexing @gifts — The gift filter index stores the base gift id and drops the enhancement level, because the index exists to answer which planners contain a gift and the level is a property of the equipped copy rather than of the containment. Content keeps the encoded form, so nothing about what a planner holds is lost. REJECTED: expanding the query term into every encoding of the gift — keeps the index faithful to content and stays fully indexed, but puts the encoding rule in the query builder as well as the writer, and the expansion factor grows with every enhancement level added. REJECTED: a stored generated column deriving the base beside the raw id — makes the canonical form underivable-by-hand and indexes cleanly, at the cost of baking the encoding into DDL, which is worse to change later than a function is.
- @indexing @gifts — The collapse is expressed twice, once in the extractor and once in the rebuild procedure, and the drift reconciler is what holds them to the same answer. Two engines write this index and neither can call the other. REJECTED: making the procedure the only writer and having Java call it — the extractor is also the oracle the reconciler audits with, so collapsing them would leave the audit comparing the procedure against itself.
- @indexing @gifts — Enhanced ids are recognised by the two bands they actually occupy rather than by being longer than a base id. The test seed carries synthetic gift ids outside every valid band, and a width test would have rewritten them into a different gift. REJECTED: treating any id above the base width as enhanced — simpler, and wrong for every id the encoding never produced.
- @schema @migration — The backfill ships in the same migration that redefines the procedure, and collapses onto existing rows with an ignoring insert so a planner already holding both forms merges into one row rather than failing the primary key. REJECTED: backfilling in a follow-up — the reconciler would restore the encoded rows from content before the follow-up ran, so the two halves are not separable in time.

## Takeaway
- takeaway: a derived index is free to disagree with its source about representation, and choosing what it forgets is what makes its queries cheap — the constraint is that everything writing it must forget the same thing.
