# 034 account-deletion-retention
epic: none · pr: none

## Decisions
- @account-delete @grace-period — Deletion is two-stage: the account is deactivated at once and erased after a 30-day grace period, and signing in during that window restores everything. Nothing is destroyed while a reversal is still possible, so the deactivation half must be expressible as state rather than as data loss. REJECTED: immediate irreversible deletion — the click that ends an account is often made in anger, and no recovery path exists once the rows are gone.
- @account-delete @visibility @catalog — Deactivation withdraws an owner's catalog rows and reactivation reinserts them, both as one statement filtered by a subquery on the owner. The browse projection is presence-as-visibility, so the listing decision is already a write-side concern and the hot read path can stay ignorant of account state. REJECTED: filtering the author join at read time — a permanent cost on every list render to serve a state that is rare and temporary. REJECTED: clearing the filter indexes alongside the catalog rows — search is rooted at the catalog, so index rows for a withdrawn planner are unreachable, and rebuilding them on restore is the expensive half.
- @account-delete @visibility @comments — A deactivated author is unattributed at the point the comment tree is assembled, not by the query that loads the authors. Comments have no visible-only projection to remove rows from, and the assembly runs on planner-detail traffic rather than browse traffic, so a predicate there is affordable where one on the list is not. REJECTED: giving comments a presence-optional projection for symmetry with the catalog — pays a projection's maintenance cost at a traffic volume that does not need it.
- @account-delete @erasure @comments — Hard delete empties a comment's text and reassigns its authorship, keeping the row. A reply addresses a parent that must still resolve, and the retained text is free-form enough to identify its author on its own. REJECTED: deleting the comment row — replies lose their parent and the thread reads as though the conversation never happened. REJECTED: keeping the text under an anonymous author — pseudonymising the authorship column does not pseudonymise the sentence.
- @account-delete @sentinel @foreign-keys — Content that outlives its author is reassigned to a sentinel account rather than to a null owner. Every read path would otherwise carry a null branch for a case that is rare and never interesting. REJECTED: nullable owner columns — moves the cost from one row in the users table to every query and every renderer.
- @account-delete @foreign-keys @delete-rule — The delete rule on each foreign key into `users` states that table's retention: `CASCADE` for rows that belong to the account, `NO ACTION` for the two comment tables that must outlive it, `SET NULL` for moderator attribution. The rule is the enforcement, so a table's policy cannot drift from its schema. REJECTED: uniform `CASCADE` — the tables needing reassignment would be carried off silently instead of refusing. REJECTED: dropping the foreign keys for a plain owner column swept by explicit `DELETE` — surrenders insert-time integrity, and with it the guarantee that no row can name an account that does not exist.
- @account-delete @order — The hard-delete sweep reassigns the `NO ACTION` tables, deletes the projections that carry no foreign key (see 015 @planner-aggregate @foreign-keys @app-sweep), and deletes the account last, letting `CASCADE` take the remainder. The two `NO ACTION` keys make the reassignment mandatory: omitting it aborts the transaction rather than orphaning a comment.

## Takeaway
- takeaway: a foreign key's delete rule is where a table's retention policy is enforced, and the rules that refuse to cascade carry the most weight — they convert a skipped cleanup step into a failed transaction instead of an orphaned row. A parent whose children all cascade documents nothing; a parent with three different rules documents three different answers to "whose data is this".
