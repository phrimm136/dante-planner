# 120 detail-cards-are-a-shared-concept
epic: none · pr: none

## Decisions
- @shared @cards @headless — The skill, passive, sanity and unit-status cards become shared rendering cores that take the entity's data and text as props, and each page keeps a thin adapter that reads its own detail data and renders the core. Identity, E.G.O and battle pages render the same cards, so no slice owns them; the cores read identity or E.G.O detail hooks today, which a shared module may not import. REJECTED: moving the detail hooks and entity types to shared along with the cards — identity-only and E.G.O-only data concepts would become shared, and shared would stop being domain-neutral. REJECTED: importing the cards through the owning slice's public entry — the owner is arbitrary and every consumer then depends on an unrelated slice. REJECTED: a battle-local copy — structure that does not vary is not copied.
- @shared @passive — One `passive` concept holds the passive card core, the generic tier selection and both the identity and E.G.O selection rules; the separate passive-selection concept is absorbed. Event sinners and a growth-tier assistant ship identity-shaped passives, so the identity rule has to be reachable outside the identity slice. REJECTED: keeping selection as its own concept beside a rendering-only passive concept — two concepts on one subject, split by kind of code rather than by subject.
- @shared @egoGift — The E.G.O gift entity core (schema, types, builder, card and its parts, list data, filter dropdown, grid) becomes a shared concept, and the E.G.O gift slice keeps only its list and detail pages. Four slices borrow it, and a module used by two or more slices lives in shared space. The singular-builder lint scope widens to cover entity builders in shared concepts. REJECTED: moving only the pieces the abnormality-event slice borrows — their dependency closure is the core itself.

## Takeaway
- takeaway: the lint answers whether an import is allowed; ownership answers whether it is right. A third consumer of a slice-owned component is the signal that it never belonged to the slice, and a component that fetches its own slice's data has to be split into core and adapter before it can leave.
