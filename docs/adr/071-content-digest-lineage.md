# 071 content-digest-lineage
epic: none · pr: none

## Decisions
- @sync @digest @identity — Planner content carries a SHA-256 digest of the wire string, stored beside it as `BINARY(32) NOT NULL`, computed exactly once by the author of the bytes — the server, in `PlannerContent.recordSave`, over the request string as received — adopted by clients from the response, and never recomputed from the stored column. MySQL re-serializes a JSON column, so the stored form is not the string that was written and a digest taken over storage answers a different question than a digest taken over the wire. REJECTED: a canonical-JSON serialization agreed between TypeScript and Java — two implementations of one normalization, kept in step forever, to reconstruct agreement on bytes both sides already exchanged verbatim. REJECTED: the existing FNV-1a `hashKey` — a 32-bit output collides around sixty-five thousand values, and a collision here reads as "no change", which is the one failure the digest exists to exclude. REJECTED: a client-computed authoritative digest — the stored value becomes a claim by the party whose content it describes rather than a fact about the bytes the server accepted.
- @sync @digest @causality — Sync classification consults the digest first — equal digests mean equal content, so the comparison ends there — and only then orders by `syncVersion`; a client adopts a version only together with the content that version describes. A version integer is a causality signal and cannot answer identity, so on its own it produces both phantom conflicts, where equal content differs only in version, and silent lost updates, where a device adopts a version carried by content the user never held. REJECTED: dropping `syncVersion` and classifying on the digest alone — identity cannot order two writes, so every divergence, including the ones ordering resolves unambiguously, would degrade into a conflict the user has to arbitrate.
- @sync @digest @backfill — The column arrives in one migration that adds it, backfills, and sets `NOT NULL`; the backfill hashes MySQL's canonical rendering, and a missing local digest in IndexedDB means "unknown, use version". A backfilled digest is taken over the re-serialized form and therefore never equals any future wire digest, so each planner and device pair pays one fall-through to version comparison after its first post-deploy save, and the pair self-heals on the next pull — a bounded, one-shot cost that no split migration would reduce.

## Takeaway
- takeaway: a version number and a content identity answer different questions, and a store that re-serializes what it was given quietly makes them the same question with no answer — hash what crossed the wire, at the only point that saw it, or the identity is a property of the storage engine's formatter.
