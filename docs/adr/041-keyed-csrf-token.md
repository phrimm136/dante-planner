# 041 keyed-csrf-token
epic: none · pr: none

## Decisions
- @auth @csrf — The double-submit token is a MAC the server can recognise as its own rather than opaque randomness, so admission asks whether this server minted the value instead of whether two attacker-reachable copies of it agree. An unkeyed token makes the check a tautology for anyone able to write either half. REJECTED: keeping the token unkeyed and relying on the name prefix alone — leaves the header-versus-cookie comparison meaningful only while no cookie-write primitive exists anywhere on the host, which is the assumption the prefix is there to stop depending on.
- @auth @csrf — The token binds to nothing user-specific, because the filter runs ahead of authentication and no stable per-user handle exists there. The consequence accepted is that an attacker who obtains a legitimately minted token of their own and can also write the victim's cookie can still transplant it. REJECTED: embedding the authenticated subject — needs the principal the filter has not resolved yet, and reordering the filter behind authentication would leave the authentication endpoints themselves unprotected. REJECTED: binding to the access or refresh cookie — both rotate on a fifteen-minute cadence, so every rotation would invalidate the token and mint a 403 for whatever request raced it.
- @auth @csrf — The cookie keeps its plain name and the deployment-wide `Domain`, because the SPA and the API are separate hosts under one registrable domain and the SPA must read the cookie from script to echo it. The `__Host-` prefix forbids `Domain` and would host-lock the cookie to the API, where the SPA's origin cannot see it; the resulting 403 on every mutation is a total outage, and the same prefix additionally requires `Secure`, which local development does not set. The consequence accepted is that a sibling subdomain able to write cookies can still plant a value. REJECTED: adopting the prefix and serving the API same-origin — a routing change reaching past this decision's blast radius, and the split is what the cookie domain exists to bridge. REJECTED: adopting the prefix without the domain — the failure is silent to the server and total for the client.
- @auth @csrf — A cookie that fails verification is replaced on the next safe request rather than merely tolerated, which is what carries browsers holding a token minted before this scheme without logging anyone out. Enforcement rejects an unrecognised cookie in the same pass, so no window exists in which a forgeable token still passes. REJECTED: accepting the old unkeyed format during a migration window — the window is exactly the period the old format is known-weak, and the ensure-cookie path repairs the browser without one.
- @auth @csrf (taste) — The signing key is HKDF-expanded from the shared secret under a purpose label rather than being the secret itself, so a token-key compromise does not extend to the sealing key and either rotates alone. REJECTED: reusing the sealing key directly — it already serves two purposes with no domain separation, and a third would deepen a coupling this record would otherwise have to unwind later.

## Takeaway
- takeaway: comparing two values an attacker can both supply proves nothing, so a double-submit check is only worth its complexity once one of the two carries evidence the server produced it.
