# 022 auth-token-architecture
epic: none · pr: none

## Decisions
- @oauth @bff — The front channel is a server-driven redirect: a start endpoint mints state and the PKCE verifier and redirects to the provider, and a callback endpoint verifies, exchanges the code, sets cookies and redirects back to the application. REJECTED: a popup with browser-side PKCE and `postMessage` — the redirect's loss of in-memory state is non-destructive here because the editor autosaves to local storage continuously, and the popup flow put the verifier in a context the page could read.
- @jwt @claims @leak — Token claims are minimized, with the subject carrying the user id. The encrypted claim blob is dropped and no token carries an email address. REJECTED: the email as subject — it is a plaintext personal identifier in a token any holder can decode, and the encrypted blob around the other claims did not cover it.
- @jwt @type-confusion — Token type is enforced structurally, by binding a required type claim into the parser itself, rather than by a guard at each consumer. REJECTED: a per-call-site type check — it has already been forgotten once (two of three refresh callers guarded, the access path unguarded), and would need re-adding on every future validation path. An invariant enforced by construction cannot be forgotten by the next caller.
- @jwt @keys @threat-model — One signing key with type-bound parsers. REJECTED: separate signing keys per token type — the threat is confusion between tokens signed by our own key, which a required claim fully defeats; separate keys buy key-leakage blast-radius isolation this single-service threat model does not need, at the cost of doubling cross-region key rotation through the secret replication pipeline.
- @jwt @neutral-parser — Helpers whose job is to read the type claim use a deliberately type-agnostic parser, because a method that discovers the type cannot run through a parser that presupposes it.
- @refresh @lineage — Refresh rotation is lineage-based, with family revocation on detected theft. REJECTED: mint-then-blacklist — it closes the concurrent-request race window without detecting a stolen token or recovering from one, and leaves users stuck rather than self-healing.
- @refresh @causality — Retry transitions bind to concrete events, such as a successor having been used, never to wall-clock time. REJECTED: an N-second retry window — an arbitrary tuning constant that brings its own edge cases and rots as latency changes.
- @refresh @supersede — A retry mints a fresh successor and supersedes the previous one. REJECTED: re-returning the stored successor to every presentation — attacker and victim then walk the chain in lockstep, and theft detection never fires for whoever rotates second.
- @refresh @family — A token family is created per login, not per device. REJECTED: a device-to-family map — the scenarios that would need device-scoped revocation on re-login are served better by an explicit "log out everywhere" action than by inferring security intent from the fact that someone logged in.
- @csrf @double-submit — Unsafe methods require a header echoing a readable cookie. REJECTED: the previous posture, which disabled framework CSRF on the unenforced assumption that all GET requests are read-only — nothing checked that assumption, and one mutating GET already exists on the OAuth callback.
- @oauth @transient-cookie — The redirect scratchpad holding state and the PKCE verifier is a short-lived signed and encrypted cookie rather than server-side storage. It is set to lax same-site deliberately: strict would not survive the provider's cross-site top-level redirect back to the callback.
- @ban @latency @threat-model — A ban takes effect within the access-token lifetime, with no per-request revocation stamp. REJECTED: a security stamp checked on every request — bans are already enforced lazily at the write layer, so a banned user holding a still-valid access token cannot mutate anything, and the stamp would put a store lookup on every authenticated read to close a window that is already harmless.

## Takeaway
- takeaway: the two recurring moves here are pushing an invariant into a place callers cannot bypass, and sizing a hardening to the actual threat rather than the theoretical maximum. The type-confusion bug is what both look like when they are absent — a check that existed, was correct, and was simply not written at the third call site.
