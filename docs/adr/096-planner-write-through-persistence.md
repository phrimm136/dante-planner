# 096 planner-write-through-persistence
epic: none · pr: none

## Decisions
- @autosave @durability @mobile — The planner editor writes IndexedDB on every store change, coalesced per task by microtask, with no debounce and no lifecycle listener. A keystroke's write is issued and committed inside the task that made it, so a page hidden or discarded a moment later has nothing left in memory. Measured cost: one commit of the edited note's subtree per store write and well under a millisecond to validate and serialise a full-size planner, so nothing here needed a timer. REJECTED: keeping the two 200ms debounces and adding a `visibilitychange` flush — on mobile the only exit signal is `visibilitychange`, `pagehide` often never fires before a discard, and a flush that awaits anything or only arms a timer loses exactly the edit it was added for; it also keeps the delivery registry, the unmount flush, the unload veto, and the in-flight queue alive for one path. REJECTED: server-side periodic autosave in the Canva style — it relocates the memory-only window to the interval before the next send, needs an adaptive throttle to keep the primary healthy, and contradicts the guest population and the single-round-trip write rule.
- @indexeddb @commit — A last-chance write calls `transaction.commit()` right after its put. Auto-commit sends the commit message only when the task ends, and a renderer killed before then takes the transaction with it: measured under a CDP `Page.crash`, a put issued in the task survived with an explicit commit and was lost without one. Creating the transaction synchronously is necessary but not sufficient.
- @autosave @status — Save status is a per-editor store the label subscribes to, not hook state. The hook is called by the shell, so state inside it re-rendered the shell's whole body plus every child fed by the hook's unstable callbacks on each write; a store scopes the update to the one label that reads it. REJECTED: keeping `isAutoSaving` and `lastSavedAt` as state — per-keystroke writes would pay that render per keystroke, and "autosaving" has no meaning when every write completes within milliseconds.
- @deviceId @schema — `metadata.deviceId` leaves the local planner. The server stamps its own `device_id` from an HTTP-only cookie and the upsert request never carried the client's value; on the client the field was written everywhere and read nowhere, and the IndexedDB read that minted it was the one await in front of every local write. The key goes on the schema's legacy strip list per ADR 086, so stored rows and old export files keep parsing. REJECTED: a version 3 IndexedDB migration rewriting every row — the strip list already covers export files, which no migration can reach, and the only leftover is one orphan singleton row that nothing reads. REJECTED: making the field optional — a field with no reader is not kept optional, it is deleted.
- @savedAt @schema — `metadata.savedAt` leaves the local planner and the planner summary, joining the legacy strip list. Its value had no reader: the label seeds from `lastModifiedAt`, the server serves the wire field from `lastModifiedAt` (ADR 017), and the only consumer, the save-status badge, read its nullness, which every client writer set exactly when status was not `saved`. The one writer that set it null regardless of status, the server summary mapper, feeds only the sync categorizer. The badge derives pending changes from status alone. REJECTED: keeping it as the "never written" witness — ADR 088 already retired that reading, and a field whose value nobody reads and whose nullness restates another field is two fields where one drifts.

## Takeaway
- takeaway: durability is decided by when the commit message leaves the renderer, not by when the code "saves"; every mechanism between a keystroke and that message — a debounce, an await, an auto-commit — is a window the platform may not grant, and deleting the mechanisms beat adding one more exit path.
