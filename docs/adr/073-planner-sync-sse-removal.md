# 073 planner-sync-sse-removal
epic: none · pr: none

## Decisions
- @sse @planner @removal — The planner created, updated and deleted event family is removed end to end: the backend stops emitting it, `SseEventType` loses the three values, `PlannerSyncEvent` and its listener are deleted, the frontend handlers and `SsePlannerPayloadSchema` are deleted, and the client's Last-Event-ID plumbing goes with them; `refetchOnWindowFocus` on the server-backed planner queries becomes the freshness mechanism in their place. The handler invalidates only queries whose query functions read IndexedDB, plus one key no query registers, so the whole chain is observably a no-op; the transport is at-most-once with no replay and per-pod registries, so no client may treat it as authoritative whatever it carries; and the versions it delivered were adopted without the content behind them, which is where phantom conflicts came from. Notifications, comments and account suspension keep their SSE, because a hint that triggers a fetch is the shape this transport supports. REJECTED: making the events real by fetching and reconciling on the signal — it buys multi-device liveness, which is rare for a single-user planning tool, at the price of a second reconciliation path beside the one that runs on load and focus. REJECTED: events that carry the payload — a full row per save to every connected device, and the shape-corruption class that arrives with any second writer into the cache. REJECTED: implementing server-side event ids so the family can be replayed — the outbox relay already covers misses on the server side and focus refetch covers them on the client side, so replay would be a third delivery guarantee over a channel that needs none.
- @sse @planner @freshness — Simultaneous editing on two devices degrades to focus-refetch freshness, and a delete performed on another device surfaces as a 404 when the stale entry is opened, which the client answers with a message rather than an error boundary. Bulk import and publish or unpublish need no device-sync event at all: each is already a mutation on the device that issued it and a refetch on any other.

## Takeaway
- takeaway: an event that only invalidates local-first caches invalidates nothing, and it takes a reading of both ends to see it — the delivery side looked correct in isolation for as long as nobody asked which query the invalidated key belongs to.
