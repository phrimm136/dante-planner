# 015 planner-aggregate-decomposition
epic: none · pr: none

## Decisions
- @planner-aggregate @foreign-keys @app-sweep — `planner_id` is the shared primary key across every aggregate and projection table, with no foreign keys among them; foreign keys point only outward, to `users` or to the write-once planner core. Deletion is an application-side batch sweep by planner id. REJECTED: foreign-key cascade among the aggregate tables — an FK child's shared lock is exactly what upgrades into the upsert deadlock below, and cascade couples deletion semantics to the storage engine.
- @planner_content @deadlock @optimistic-lock — The owner hot path writes only `planner_content`, and no table foreign-key-references it. REJECTED: keeping owner-mutated columns on a row that FK children reference — a same-transaction child insert takes a shared lock that upgrades to exclusive, deadlocking two racers in every one of 80 reproduction attempts. REJECTED: `@DynamicUpdate` and dropping secondary indexes — both left the reproduction at 80/80; only isolating the hot row into a PK-only table brought it to 0/80.
- @planner_stats @counters — Counters live only in `planner_stats` and are authoritative there outright. REJECTED: a transitional dual-write with a non-updatable guard and a reads-enabled flag — a stop-the-world migration lets the new table be authoritative immediately, with no half-migrated state to carry, reason about, or later remove.
- @projection-maintenance @async @read-your-writes — Projection maintenance splits by cost: the cheap scalar copy into the catalog is written synchronously inside the write transaction, while the expensive filter rebuild defers to an after-commit listener in its own transaction, batched, and skipped entirely when content composition is unchanged. REJECTED: fully synchronous maintenance — six statements at cross-region latency is a multi-second write. REJECTED: deferring the scalar copy too — it breaks read-your-writes for a title edit appearing in the author's own list.
- @aggregate @cqrs @ddd — A rich, root-coordinated write aggregate enforces cross-entity invariants at the root, paired with deliberately dumb read projections; the counter table is the sanctioned exception, using atomic increments rather than load-mutate-save. REJECTED: making every entity rich — read projections gain nothing from behavior. REJECTED: an anemic aggregate with the logic in services — it scatters the invariants across the service layer, which is the state this decomposition exists to leave.

## Takeaway
- takeaway: write contention is a property of the row shape, not of the query. Splitting the hot column set onto a row that nothing references was the only intervention that moved a reproducible deadlock, after two plausible ones that changed nothing measurable.
