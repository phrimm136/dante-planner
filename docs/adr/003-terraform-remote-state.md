# 003 terraform-remote-state

epic: none · pr: none

## Decisions
- @terraform @state @workspaces — every stack keeps state in one S3 bucket. Local state blocks CI from planning at all, but the forcing constraint is correctness rather than automation: `terraform_remote_state` over `backend = "local"` reads a literal filesystem path, which resolves to the *default* workspace whichever workspace is selected. A `staging` workspace of `terraform/seoul` would have wired itself to *production* Oregon's VPC, peering and RDS, silently and with no error. `workspace_key_prefix` on both the backend blocks and the remote-state data sources resolves per workspace. REJECTED: keeping local state and forbidding workspaces — the cross-stack reads are already wrong for any second environment, and the prohibition lives nowhere the tool can see it. REJECTED: passing cross-stack values through tfvars instead of remote state — trades a silent misresolution for a hand-copied value that drifts, and the stacks already committed to "few manual touch".
- @terraform @state @bootstrap — the bucket is created by `iam-bootstrap`, which is therefore the one stack that keeps local state. Storing its own state in the bucket it creates is circular, and it must stay appliable from a laptop holding nothing but credentials. REJECTED: a separate `state-bootstrap` stack — a second stack with the same chicken-and-egg property, so the count of locally-stated stacks stays one either way.
- @terraform @state @locking — locking is S3-native (`use_lockfile`), available from Terraform 1.10 and satisfied by the pinned `>= 1.6` floor plus the installed 1.15. REJECTED: a DynamoDB lock table — one more resource to create before the backend works, for a guarantee S3 now provides directly.
- @terraform @accounts @guard — every AWS provider takes `allowed_account_ids`, sourced from an explicit variable. A workspace isolates state and nothing else: literal paths, account-global IAM names and the ambient credential chain all cut straight through it, so `terraform workspace select staging` with production credentials still plans against production. REJECTED: deriving the id from `aws_caller_identity` — it reports the account the credentials already named, so the assertion would be a tautology.
- @terraform @state @accounts @secrets — state lives in the account whose resources it describes, so the bucket count tracks the account count and no account reads another's state. Terraform serializes every attribute it manages, including the ones providers mark sensitive, so a state file carries the database master password and the tunnel credentials in plaintext. REJECTED: a single bucket in the management account with member stacks assuming a role inward — fewer buckets, and one backend configuration serving every stack, but it gathers every environment's secrets into the single account service control policies cannot constrain, so one compromise reaches all of them at once. REJECTED: one bucket partitioned by key prefix — a prefix is a convention rather than a boundary, so a misconfigured one is a silent cross-environment write, where a wrong account fails at the first call.

## Takeaway
- takeaway: the failure the backend move actually prevented was never visible as a failure. Both halves of the wiring — the backend block and the `terraform_remote_state` data source — have to move together, and moving only the first leaves a configuration that plans clean, applies clean, and points a staging environment at production's network.
- takeaway: a state file is a secrets store nobody declared, because serializing a resource graph necessarily serializes the credentials inside it. Where state lives is an access-control decision wearing a convenience decision's clothes.
