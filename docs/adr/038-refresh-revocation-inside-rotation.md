# 038 refresh-revocation-inside-rotation
epic: none · pr: none

## Decisions
- @auth @revocation — The user-invalidation stamp is read inside the atomic rotation script alongside the family revocation marker, so "logging out everywhere stops rotation" is an invariant the primitive enforces rather than a check every caller must remember. The lineage rotation path is reached from three call sites and none of them consulted the stamp, because the flag that moved the read path off the legacy branch left the legacy branch's checks compiling but unreachable. REJECTED: adding the check to each caller — restores the property in exactly the shape that already failed once, and the next path added inherits the same omission. REJECTED: consulting the stamp before invoking the script — reopens the check-then-act window the single round trip exists to close.
- @auth @revocation — Logging out everywhere revokes nothing per-family and relies solely on the stamp. No user-to-family index exists, and building one means a set write on every mint plus a fan-out delete on every logout-all, to answer a question one string read already answers. REJECTED: maintaining `rt:ufam:<user>` as a family set — buys defence in depth against a stamp that fails to write, at the cost of a second consistency problem between the set and the families it names.
- @auth @legacy — Logout revokes the family a legacy refresh token would be admitted into, recomputing the deterministic synthesis that admission itself uses, because such a token carries no family of its own and the presented cookie is the only evidence available. REJECTED: blacklisting the legacy token — the write already happens and the lineage path never reads it, which is the defect rather than the fix. REJECTED: refusing legacy tokens outright at logout — leaves a live credential in the browser until natural expiry, which is the window logout exists to close.
- @auth @redis (taste) — The script addresses two keys carrying no common hash tag, pinning the auth Redis to a single-node deployment; a move to a cluster requires re-keying, not re-logic. REJECTED: placing the stamp under each family's hash tag — the stamp is per-user and families are per-session, so one user's stamp would need a copy in every family's slot and every copy is a write to keep coherent.
- @observability — A stamp-driven rejection carries its own outcome tag rather than reusing the revoked-family one, so a deliberate logout-everywhere and a theft-driven family revocation stay separable in the rotation counter. REJECTED: one shared rejection tag — collapses a routine user action and a suspected compromise into a single line on a dashboard.

## Takeaway
- takeaway: a revocation check placed outside the primitive it protects survives every refactor except the one that moves the read path, and that is the refactor a feature flag performs silently.
